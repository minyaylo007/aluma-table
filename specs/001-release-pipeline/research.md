## R1 [флот]. Модель доставки: pull по git-ссылке окружения (вариант D)

**Decision.** Желаемое состояние окружения — ветка `production` в репозитории, указывающая на коммит выпущенного тега
`vX.Y.Z`. Конвейер двигает её вперёд при деплое и назад при откате (право записи — только у задания деплоя).
Агент на машине раз в минуту анонимно читает `refs/heads/production` и `refs/tags/v*` протоколом git v2 с фильтром
по префиксу; при сдвиге скачивает артефакт релиза по прямой ссылке `github.com/<repo>/releases/download/<tag>/…`.
REST API агенту не нужен вообще; Deployments API использует только конвейер (решение дирижёра, Q6).

**Rationale.** Не требует входящего SSH и правок firewall на чужом сервере; агент ничего не слушает; у агента нет
секретов; git smart HTTP и ссылки скачивания релиза не расходуют лимит REST API (замер), поэтому любое число агентов
флота на одном IP укладывается; задержка ≈ 1 мин; изменяемых объектов в релизах нет.

**Alternatives considered.**
- **A — опрос Deployments API.** Анонимный 304 расходует лимит (замер) → флот из трёх агентов при опросе раз в 2 мин
  = 90/ч > 60. Влезает только раз в 6 мин (задержка до 7 мин) и всё равно делит лимит с любым будущим клиентом на IP.
- **B — файл «желаемая версия» в изменяемом пре-релизе.** Лимит не расходует, но вводит изменяемый объект среди
  неизменных релизов и ещё одну движущуюся часть.
- **C — узкий read-only токен агенту (5000/ч).** Противоречит решению владельца (Q3): на машине не должно быть токенов
  GitHub у агента.
- **Self-hosted runner на ace-main.** Постоянный исходящий long-poll-процесс, который исполняет код из репозитория
  (после публикации — в т. ч. из PR чужих форков при ошибке настройки) под пользователем, у которого есть
  административные права на машине; обновляется сам; в стандарте флота — лишний класс риска на машине с четырьмя
  чужими бизнесами. Отвергнут.
- **SSH из Actions на машину.** Требует входящего SSH-доступа, ключа в GitHub Secrets и правил firewall — это «да»
  Дениса и чужой сервер. Отвергнут дирижёром.

## R2 [флот]. Как агент читает ссылки — без учётных данных и без лимита

**Decision.** `git ls-remote https://github.com/<repo> refs/heads/production 'refs/tags/v*'` с изолированной
конфигурацией: переменные `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`,
`GIT_ASKPASS=/bin/false`, ключи `-c credential.helper= -c protocol.version=2`. Для аннотированных тегов берётся
«очищенный» sha (`^{}`). Скачивание — `urllib` без заголовка `Authorization`, только `https://github.com/…`
(редиректы на `objects.githubusercontent.com` разрешены, на другие хосты — нет).

**Rationale.** Помощник учётных данных `gh` настроен у пользователя глобально — без изоляции git мог бы подставить
токен владельца. Протокол v2 отдаёт только запрошенные ссылки (у старого протокола ответ — все ссылки репозитория,
у публичного репо с PR — сотни килобайт: у `octocat/Hello-World` 233 КБ). Отказы/замедления GitHub на анонимный git —
агент пропускает цикл и увеличивает интервал (до 10 мин), машину не трогает.

**Alternatives.** Свой разбор smart HTTP через `urllib` — нет git-конфига вовсе, но больше кода и свой парсер
pkt-line; держим как запасной путь, если изоляция git окажется ненадёжной.

## R3 [флот]. Статус деплоя в GitHub — встроенными правами конвейера по публичному health

**Decision.** Задание `deploy` объявляет `environment: production` — GitHub сам создаёт Deployment и ставит ему
статус по итогу задания (в процессе → успешно / провал; предыдущие успешные — неактуальны; отменённое задание —
отменён). Задание: проверяет, что тег и полный набор файлов релиза есть; двигает `production`; затем раз в 20 с
опрашивает публичный адрес health (переменная репозитория `ALUMA_HEALTH_URL`) до 15 минут и завершается успехом
только при совпадении `version` = тег И `git_sha` = полный sha тега. `concurrency: deploy-production`,
`cancel-in-progress: true` — новый деплой отменяет ожидание старого.

**Rationale.** Нет ручных вызовов Deployments API и нет личных токенов; окружение показывает активную версию;
провал на машине (агент откатился) виден как таймаут наблюдателя.

**Риски и как закрыты.**
- *Ответил не тот стек* (до переключения DNS `table` смотрит в AWS; кеш; старый процесс) — требуется совпадение и
  номера, и полного sha; AWS отдаёт `0.3.0` без sha → только провал, никогда ложный успех. Адрес — переменная
  окружения `production`; с переключения DNS 11.09 (`a7e9c64`) — `table`.
- *Подмена ответа* — HTTPS до нашего Caddy; подделать sha без контроля над сервером нельзя; ложный провал не
  трогает машину.
- *Задержка* — агент ≤ 2 мин + установка ≤ 2 мин + сборка/релиз; таймаут 15 мин с запасом (SC-001 — 20 мин).
- *Отказ GitHub Actions* — машина продолжает работать на текущей версии; повтор — действием отката/деплоя.

**Alternatives.** Агент сам пишет статусы — нужен токен (отвергнуто, Q3). Отдельные ручные вызовы Deployments API из
workflow — дублируют то, что GitHub делает для `environment:` сам.

## R4 [флот]. Правила репозитория на публичном репо: master, теги `v*`, ветка `production`

**Decision.** После смены видимости (R8 — сначала проверка истории):
- ruleset `master`: только через PR, обязательные проверки (`lint`, `test (3.12)`, `test (3.13)`, `build`,
  `browser`), 0 одобрений, запрет force-push и удаления, **без обходов** (Q2);
- ruleset тегов `v*`: создание — только конвейер (исключение для приложения GitHub Actions), обновление и удаление —
  никто;
- ruleset `production`: запись — только конвейер (исключение для GitHub Actions), удаление — никто; перезапись
  (откат) разрешена только исключению;
- авто-merge включён, метод слияния — squash (линейная история, заголовок PR = сообщение коммита в стиле проекта),
  ветки после слияния удаляются;
- окружение `production`: развёртывание только из `master` (правило веток окружения) — откат, запущенный с другой
  ветки, не пройдёт;
- сканирование секретов и защита от их push — включены;
- неизменяемые релизы (настройка репозитория «immutable releases») — включить, если доступна; проверить в пилоте.

**Риск.** Можно ли в личном публичном репо дать исключение в ruleset именно встроенному `GITHUB_TOKEN` (приложению
GitHub Actions) — **проверяется реальным прогоном в пилоте**. Запасной вариант (согласован с дирижёром): ветка
`production` без правила, а безопасность держится на агенте — он ставит только коммит, на который указывает
опубликованный тег `v*` с полным набором файлов релиза и совпавшими суммами; теги `v*` защищены от удаления и
перезаписи. Тогда подвинутая руками ветка поставит лишь уже выпущенную конвейером версию. Если исключение не работает
и для тегов — релизный тег ставится конвейером, а правило тегов ограничивается запретом обновления и удаления.

## R5 [флот]. Номер версии

**Decision.** SemVer `vX.Y.Z`. Скрипт `scripts/next_version.py`: берёт наибольший тег `v*`, метки PR слитого
коммита (`release:major` > `release:minor` > иначе patch) и выдаёт следующий номер; без тегов — `v0.5.0`. Метки PR
читает задание релиза встроенным токеном (`GET commits/<sha>/pulls`). Задание релиза — `concurrency:
release-production`, без отмены: два слияния подряд дают две версии по порядку. CI на master не отменяется новым
прогоном (`cancel-in-progress` только для не-master), иначе релиз мог бы оборваться посередине.

**Alternatives.** Conventional commits → номер (release-please, semantic-release) — новые зависимости и правила
сообщений, которых в проекте нет. CalVer — отвергнут дирижёром (Q4).

## R6 [флот]. Артефакт: воспроизводимый архив + суммы

**Decision.** Файлы релиза: `aluma-vX.Y.Z.tar.gz` и `SHA256SUMS`. Архив собирает `scripts/release_build.py`
детерминированно (порядок имён, `mtime` = время коммита, владелец 0:0, `gzip` без имени и времени): дерево коммита
(`git archive`), собранная `dist/`, `RELEASE.json` (версия, sha, режим сборки), `RELEASE.env` (`APP_VERSION`,
`GIT_SHA` — не секреты) и `MANIFEST.sha256` (сумма каждого файла архива). Проверки: повторная сборка того же коммита
даёт побайтно тот же архив; в архиве нет `data/`, `dump*`, `.env`, `infra/samconfig.toml`, `node_modules/`.

**Rationale.** Опубликованное = поставленное: агент ничего не собирает; `MANIFEST.sha256` даёт и проверку
распаковки, и «проверку на ручные правки» каталога версии (R14).

**Alternatives.** Отдельные архивы кода и статики — две сущности на одну версию. Аттестация происхождения
(`actions/attest-build-provenance`) — полезна, но проверка на машине требует `gh` с авторизацией; можно публиковать
как дополнение, агенту не нужна.

## R7 [флот]. Линтер

**Decision.** Python — `ruff` (закреплённая версия в `requirements-lint.txt`, один wheel без зависимостей), конфиг
`ruff.toml` с узким набором правил, дающим ноль замечаний на master: `E9` (синтаксис) и `F` (pyflakes: неопределённые
имена, неиспользуемые импорты и т. п.); расширение — отдельными PR. JS — `node --check` для `site/assets/*.js` и
`tests/*.js` (встроено в Node, зависимостей нет).

**Rationale.** Самое лёгкое из распространённого; быстрое; не тянет дерево пакетов.

**Alternatives.** flake8 (несколько пакетов, плагины), pyflakes отдельно (медленнее, без будущего роста), pylint
(тяжёлый, много шума), eslint (десятки npm-пакетов) — отвергнуты по «лёгкости» (FR-004a).

## R8 [флот]. Проверка истории перед публикацией

**Decision.**
1. Свежий `git clone --mirror` репозитория с GitHub во временную папку вне дерева (0700): так в проверку попадают
   ВСЕ ссылки, которые станут публичными, включая `refs/pull/*`.
2. `gitleaks` (закреплённая версия, бинарник с проверкой суммы из его релиза, во временной папке, в репозиторий не
   кладётся): `gitleaks git --log-opts=--all --redact` с отчётом JSON; значения замаскированы.
3. `scripts/secret_scan.py` (stdlib): по `git log --all -p` зеркала ищет шаблоны проекта — ключи AWS (`AKIA…`,
   `aws_secret_access_key`), токены GitHub/Telegram, `ADMIN_PASS=`, `IP_SALT=`, `EDGE_SECRET=`, `TELEGRAM_BOT_TOKEN=`
   с непустым значением, файлы `.env`, `infra/samconfig.toml`, `dump/*.jsonl`, `data/*.db`, телефоны (форматы
   +972/05x, +380/0xx), ключи `name`/`phone` в JSON-строках, AWS account id (12 цифр рядом с `arn:aws`) и ARN.
   Печатает только правило, коммит, путь, номер строки — **никогда значение**.
4. GitHub-сторона, которая станет публичной: журналы и артефакты прошлых прогонов Actions (`gh run view --log` →
   те же два сканера), релизы, issues, PR и комментарии.
5. Отчёт без значений — `specs/001-release-pipeline/secret-scan-report.md`; сырые выводы — только во временной
   папке, удаляются после.
Любая находка — стоп и решение дирижёра (ротация / чистка истории), видимость не меняется. AWS account id и ARN
сертификата в `infra/samconfig.toml.example` — заведомые находки, решение дирижёра (Q1).

**Rationale.** gitleaks — один статический бинарник, сканирует всю историю, умеет маскировать значения. Свой скрипт
закрывает персональные данные, которых нет в общих правилах.

**Alternatives.** trufflehog — «проверка» найденных ключей отправляет их провайдерам (исходящий вызов с секретом),
тяжелее; git-secrets — только шаблоны AWS; только сканирование секретов GitHub — работает лишь после публикации, то
есть поздно. GitHub secret scanning и push protection включаются после публикации как вторая линия.

## R9 [флот]. Устройство проверок (образец — CI УЗД, ветка `ci-checks` в `~/repos/uzd-ap`)

**Decision.**
- `ci.yml`: `on: push` (все ветки, кроме master), `pull_request` (в master), `workflow_call`; `permissions: contents:
  read`; `concurrency: ci-<workflow>-<ref>`, `cancel-in-progress` только не для master.
- Задания: `lint`, `test` (матрица Python 3.12 — как на машине, 3.13 — как в Lambda), `build` (preview-сборка, код 0,
  и повторная сборка — те же суммы), `browser` (`npm ci` из `package-lock.json`, Chromium, `tests/redesign.spec.js`
  на `PREVIEW_PORT=8007`).
- Зависимости — только из файлов: `api/requirements.txt`, `tests/requirements.txt` (новый: `werkzeug`, `boto3`,
  `moto` — закреплённые версии), `requirements-lint.txt`, `package-lock.json`.
- Actions: `actions/checkout@v6`, `actions/setup-node@v6` (Node 24; УЗД проверил прогонами 34599436737,
  34599597716); `actions/setup-python@v6` — подтвердить первым прогоном в пилоте; итог — в `docs/DELIVERY.md`.
- `release.yml`: `on: push` в master → `checks` (вызов `ci.yml`) → `release` (`contents: write`) → `deploy`
  (вызов `deploy.yml`). Релиз и деплой невозможны без зелёных `checks` этого же коммита.
- `deploy.yml` (`workflow_call`, вход `tag`) и `rollback.yml` (`workflow_dispatch`, вход `version`) — одно задание
  деплоя на оба пути.
- Без Pillow: CI не ставит Pillow, как и системный `python3` машины, которым собрана нынешняя статика `/srv/aluma`
  (иначе `image_size()` в `build.py` дала бы другие размеры). Паритет проверяется в пилоте `compare_sites.py`
  (архив релиза против `/srv/aluma`).

**Alternatives.** Релиз по `workflow_run` после CI — ещё один механизм связки и запуск файла из ветки по умолчанию;
отдельные файлы с `needs` через `workflow_call` проще и нагляднее для шаблона.

## R10 [ALUMA]. Раскладка на машине: каталоги версий + ссылка `current`

**Decision.**
```
/opt/ihor/aluma-table/
├── releases/vX.Y.Z/     распакованный артефакт (неизменный; сверяется с MANIFEST.sha256)
│   └── .venv -> ../../venvs/<sha256(requirements-server.txt)[:12]>
├── venvs/<hash>/        venv по набору зависимостей (общий у версий с одинаковым файлом)
├── current -> releases/vX.Y.Z   переключается атомарно (новая ссылка + rename)
├── state/  (0700)       agent.lock, state.json, failed.json, deploy.log, downloads/
├── data/   (0700)       живая база — не трогается никогда
└── (прежний клон, .venv, dump-*, rollback/, dns-* — остаются как есть; уборка — вне фичи)
```
Юниты: `WorkingDirectory=/opt/ihor/aluma-table/current`, `ExecStart=…/current/.venv/bin/gunicorn …`; то же для
purge. Хранится 10 последних версий (текущая и предыдущая — всегда) и venv, на которые они ссылаются.

**Rationale.** Атомарное переключение и мгновенный откат на уже распакованную версию без сети; поставленное = релиз
(суммы); код не берётся из git — агенту не нужен ни ssh-ключ пользователя, ни токен; venv по хешу не пересобирается,
если зависимости не менялись.

**Alternatives.** `git fetch` + `checkout` тега в текущем клоне (как сейчас вручную): второй источник кода помимо
артефакта; fetch по ssh — ключ пользователя (учётные данные), по https — нужна изоляция git; откат требует сети.
venv в каждом каталоге версии — ~100 МБ × 10 и установка из сети при каждом деплое.

**Переход с `0.4.0-box`.** Разово, сессией-исполнителем: поставить юниты агента, прогнать `--dry-run`, затем
`--once` на `v0.5.0` — агент кладёт новые юниты API/purge (с `current`), переключает, проверяет. «Предыдущая версия»
для этого шага — прежний клон: откат описан вручную в `docs/DELIVERY.md` (вернуть прежние юниты, перезапуск).

## R11 [ALUMA]. Номер и sha в `/api/fx/health`

**Decision.** `api/handler.py`: `GIT_SHA = os.environ.get("GIT_SHA") or None`; health →
`{"ok": true, "version": APP_VERSION, "git_sha": GIT_SHA, "ts": …}`. Юнит API читает второй файл окружения
`EnvironmentFile=/opt/ihor/aluma-table/current/RELEASE.env` **после** `aluma.env` (позднее значение побеждает) —
`APP_VERSION` и `GIT_SHA` приходят из версии, файл с секретами не правится. В Lambda `GIT_SHA` не задан → `null`
(поведение одинаково в обоих средах). Подпись версии в `/admin` сейчас `v{APP_VERSION}` — при номере `v0.5.0` было
бы `vv0.5.0`; вывод без повторной `v`. Критичные потоки (заявка, вход в `/admin` и cookie, хранилище, EDGE_SECRET)
не меняются.

**Alternatives.** Агент правит `APP_VERSION` в `aluma.env` — запись в файл с секретами (FR-019 запрещает). Номер из
файла `RELEASE.json`, читаемого хендлером, — логика, специфичная для среды выполнения (CLAUDE.md §1 запрещает).

## R12 [ALUMA]. Установка статики и локальная проверка

**Decision.** Порядок: venv → юниты (если изменились) → переключение `current` → `systemctl --user restart
ihor-aluma-api` → локальный health (до 60 с: `ok`, `version`, `git_sha`) → `rsync -a --delete-after --delay-updates
--chmod=D0755,F0644 current/dist/ /srv/aluma/` → проверка: суммы файлов `/srv/aluma` = суммы `dist/` из
`MANIFEST.sha256`, `find /srv/aluma ! -perm -o=r` пусто. Провал любого шага после переключения → возврат: прежний
`current`, прежние юниты, перезапуск, health прежней версии, `rsync` прежней `dist/`.

**Rationale.** Флаги rsync — те же, что проверены 11.09 (deploy/README.md «Публикация статики»); API раньше статики —
новая страница не обращается к ещё не поставленному API. Проверка статики — по файлам, без запросов через Caddy.

## R13 [ALUMA]. Юниты и перезапуск

**Decision.** Новые пользовательские юниты `ihor-aluma-deploy.service` (`Type=oneshot`, `ExecStart=/usr/bin/python3
/opt/ihor/aluma-table/current/deploy/agent/pullagent.py --config …/current/deploy/agent/aluma.json --once`,
`NoNewPrivileges=true`, `UMask=0027`) и `ihor-aluma-deploy.timer` (`OnBootSec=2min`, `OnUnitInactiveSec=60s`). Агент
перезапускает только `ihor-aluma-api` и только через `systemctl --user`; изменения файлов `deploy/systemd/user/`
версии копирует в `~/.config/systemd/user/` и делает `systemctl --user daemon-reload`. Агент живёт в каталоге версии
и обновляется вместе с ней; сломанная версия агента лечится запуском агента предыдущей версии вручную
(`docs/DELIVERY.md`).

## R14 [флот]. Поведение агента по образцу `deploy-uzd` (`/usr/local/bin/deploy-uzd`)

**Decision.** Отказ при ручных правках: каталог текущей версии сверяется с её `MANIFEST.sha256`, расхождение → стоп
с перечнем первых 5 путей (без содержимого), установка не выполняется. `--dry-run`: читает ссылку, качает и сверяет
артефакт, печатает «было → станет», ничего не переключает. Журнал — строка JSON на каждое действие в
`state/deploy.log` и в journald: когда, инициатор (`production`-ссылка / ручной запуск), sha было → стало, итог,
причина. Короткий итог в stdout. Отличие от УЗД: без sudo и чужого пользователя, всё под `ihor`, пользовательские
юниты; вместо `reset --hard` — переключение каталогов версий.

## R15 [флот]. Защита журнала и секретов агента

**Decision.** Агент не читает `aluma.env` и `data/`; в журнал пишет только номера, sha, пути внутри своих каталогов,
коды. Тесты агента проверяют: ни одного `Authorization`, git вызывается с изолированной конфигурацией, в коде нет
`sudo`, `caddy`, `2019`, `bind`/`listen`.
