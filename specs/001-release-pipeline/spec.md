# Feature Specification: Выпуск и деплой ALUMA через GitHub

**Feature Branch**: `001-release-pipeline` (папка фичи; отдельной git-ветки Spec Kit не создаёт)

**Created**: 2026-09-11

**Status**: Clarified

**Input**: User description: "Полный цикл поставки ALUMA через GitHub после переезда на ace-main — проверки на каждый PR и push, сборка и тесты, публикация версии (тег + GitHub Release с собранным артефактом и контрольными суммами) после попадания в master, автоматический деплой этой версии на ace-main, статус деплоя виден в GitHub, откат на любую предыдущую версию одним действием, секреты — только в GitHub Secrets; плюс документация процесса. Для владельца и всех будущих сессий: изменение уходит в прод без ручных шагов и так же просто откатывается."

## Контекст и термины

- **Коробка** — сервер ace-main, на котором ALUMA работает под пользователем `ihor`: код в `/opt/ihor/aluma-table`,
  API — пользовательский сервис `ihor-aluma-api` на 127.0.0.1:8005, статика — в `/srv/aluma`, живая база — в `data/`,
  окружение с секретами — `~/.config/aluma/aluma.env`. С 2026-09-11 (переключение DNS, коммит `a7e9c64`) гости
  попадают на коробку по основному имени `table.central-aparts.store`; проверочное имя `table-new` тоже ведёт на неё.
  Эта фича ставит версии на коробку и DNS не трогает.
- **Версия** — один выпуск ALUMA с номером вида `vX.Y.Z` (SemVer); этот номер и полный git sha коммита версии
  показывает `GET /api/fx/health`.
- **Выпуск (релиз)** — опубликованная в GitHub версия: тег, страница релиза, собранный артефакт и контрольные суммы.
- **Деплой** — постановка конкретной версии на коробку. Запрос деплоя и его статус живут в GitHub (окружение
  `production`).
- **Агент деплоя** — программа на коробке, которая сама забирает из GitHub запросы деплоя, ставит версию и проверяет
  её локально. У агента **нет никаких учётных данных GitHub**: репозиторий публичный, агент анонимно читает ссылку
  окружения по протоколу git и скачивает релизы по прямым ссылкам; REST API ему не нужен. Модель «pull»: GitHub на
  коробку не заходит, коробка ничего не слушает.
- **Ссылка окружения** — git-ветка `production` в репозитории, указывающая на коммит опубликованной версии, которая
  должна стоять на коробке. Её двигает только конвейер: вперёд при деплое, назад при откате.
- **Наблюдатель деплоя** — шаг конвейера в GitHub, который после создания запроса деплоя ждёт, пока публичный адрес
  health покажет номер и sha этой версии, и ставит статус деплоя встроенными правами конвейера.
- **Откат** — новый деплой ранее выпущенной версии.

### Стандарт флота и специфика ALUMA

ALUMA — пилот CI/CD для всего флота (`~/maestro/cicd/PLAN.md`, «Стандарт флота»). Требования помечены:

- **[флот]** — выведены из стандарта флота; одинаковы для сайта, бек-офиса и следующих проектов и пойдут в шаблон

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Публичный защищённый master: в него попадает только проверенное (Priority: P1)

Сначала вся история репозитория проверяется на секреты и персональные данные; только после чистой проверки
репозиторий становится публичным и получает защиту master. Дальше сессия или владелец вносит изменение через ветку
и pull request. На каждый push и на каждое обновление PR GitHub сам запускает проверки: линтер, полный набор
Python-тестов, сборку сайта, мокнутые браузерные тесты. Пока проверки не зелёные, PR нельзя влить. Когда зелёные —
PR вливается автоматически (авто-merge), без ожидания человека. Прямой push в master и перезапись его истории
невозможны ни для кого, включая владельца.

**Why this priority**: Всё остальное (релиз, автодеплой) имеет смысл только если в master не попадает сломанное, а
на бесплатном тарифе серверная защита master есть только у публичного репозитория. Публикация без проверки истории
раскрыла бы секреты или данные заявок навсегда.

**Independent Test**: Проверка истории даёт отчёт без находок (или находки ушли дирижёру и видимость не менялась).
После смены видимости: PR с заведомо падающим тестом (или замечанием линтера) влить нельзя; исправленный PR
вливается сам; прямой push в master отклоняется сервером GitHub.

**Acceptance Scenarios**:

1. **Given** репозиторий ещё приватный, **When** проверка истории нашла секрет, персональные данные или
   инфраструктурный идентификатор, **Then** видимость не меняется, находки (без значений) переданы дирижёру.
2. **Given** проверка истории чистая и дирижёр объявлен, **When** видимость меняется на публичную, **Then** в тот же
   шаг включаются защита master, окружение `production` с правилами и сканирование секретов GitHub.
3. **Given** PR с изменением, у которого падает хотя бы один тест или линтер, **When** проверки завершились, **Then**
   PR помечен непрошедшим, слияние заблокировано, авто-merge не срабатывает.
4. **Given** PR с включённым авто-merge, **When** все обязательные проверки зелёные, **Then** PR вливается в master без
   участия человека.
5. **Given** любая учётка, включая владельца, **When** она делает push напрямую в master или `push --force`, **Then**
   GitHub отклоняет push, история master не меняется.
6. **Given** push в любую ветку (с PR или без), **When** push принят, **Then** в GitHub видны результаты тех же проверок.

### User Story 2 - Каждое попадание в master публикует версию (Priority: P2)

После слияния в master, если проверки на этом коммите зелёные, GitHub сам присваивает следующий номер версии, ставит
тег, собирает сайт и публикует релиз: страница релиза со списком изменений, архив-артефакт с тем, что будет стоять на
коробке, и файл контрольных сумм. Любую опубликованную версию можно скачать и проверить побайтно.

**Why this priority**: Версия — единица деплоя и отката. Без неизменного опубликованного артефакта нельзя ни
надёжно поставить, ни вернуть «ровно то, что было».

**Independent Test**: Влить в master безобидное изменение — появляется новый тег и релиз с артефактом и суммами;
суммы скачанного артефакта совпадают с опубликованными; повторная сборка того же коммита даёт те же суммы статики.

**Acceptance Scenarios**:

1. **Given** новое слияние в master без метки версии, **When** проверки на master зелёные, **Then** в течение
   10 минут появляется версия с повышенным patch: тег, релиз, артефакт, контрольные суммы.
2. **Given** слитый PR с меткой `release:minor` (или `release:major`), **When** публикуется версия, **Then** повышен
   minor (major), младшие части обнулены.
3. **Given** проверки на master красные (например, из-за гонки двух слияний), **When** релиз должен был начаться,
   **Then** версия не публикуется, деплоя нет, и это видно в GitHub.
4. **Given** опубликованная версия, **When** кто-то пытается опубликовать тот же номер повторно или заменить её
   артефакт, **Then** это не происходит: опубликованные версии неизменны.
5. **Given** опубликованный артефакт, **When** его суммы сверяют с файлом сумм, **Then** они совпадают.

### User Story 3 - Опубликованная версия сама встаёт на коробку (Priority: P3)

Публикация версии создаёт в GitHub запрос деплоя в окружение `production`. Агент на коробке без всяких учётных данных
замечает его, скачивает артефакт, сверяет контрольные суммы, ставит код и статику, перезапускает сервис API и
проверяет здоровье локально: сервис отвечает, `health` показывает номер и sha новой версии, сайт отдаётся. Если
локальная проверка не прошла — агент сам возвращает предыдущую рабочую версию. Тем временем наблюдатель деплоя в
GitHub ждёт, пока публичный адрес health покажет номер и sha этой версии, и ставит деплою «успешно» либо, по
таймауту, «провал» — это видно на странице окружения и в самом деплое.

**Why this priority**: Это и есть «изменение уходит в прод без ручных шагов» — главное решение владельца.

**Independent Test**: Создать запрос деплоя на уже опубликованную версию — через несколько минут health на коробке
показывает её номер и sha, в GitHub деплой «успешен». Подложить версию, которая не проходит проверку здоровья, —
коробка возвращается на прежнюю версию, деплой в GitHub «провален».

**Acceptance Scenarios**:

1. **Given** опубликована новая версия, **When** агент выполнил очередной опрос, **Then** версия установлена,
   локальный и публичный `health` показывают её номер и sha, наблюдатель ставит деплою «успешно», в окружении
   `production` активна она.
2. **Given** контрольная сумма скачанного артефакта не совпадает, **When** агент проверяет артефакт, **Then** ничего
   не ставится; публичный health не меняется, наблюдатель по таймауту ставит «провал».
3. **Given** после установки локальный health не отвечает или показывает не тот номер/sha, **When** истёк отведённый
   срок проверки, **Then** агент возвращает предыдущую рабочую версию, проверяет её здоровье и больше не пытается
   ставить этот запрос деплоя; наблюдатель ставит «провал».
4. **Given** между двумя чтениями ссылка окружения сдвинулась дважды (два деплоя подряд), **When** агент читает её,
   **Then** ставится только последняя версия, наблюдатель более старого деплоя помечает его неактуальным, и
   одновременно двух установок не идёт никогда.
5. **Given** агент работает, **When** проверяют, что он делает на машине, **Then** он не слушает ни одного порта,
   не использует sudo, не трогает Caddy, не читает никаких токенов GitHub и ничего вне территории ALUMA.

### User Story 4 - Откат на любую прежнюю версию одним действием (Priority: P4)

Владелец или сессия с правом записи в репозиторий запускает в GitHub действие «откат», выбирает номер ранее
опубликованной версии — и она встаёт на коробку тем же путём, что и обычный деплой, с той же проверкой здоровья и
тем же статусом в GitHub. Возврат обратно на новую версию — такое же одно действие.

**Why this priority**: Автоматический откат (история 3) покрывает только провал проверки здоровья; ошибки, которые
заметил человек (не та вёрстка, неверный текст), откатываются вручную — и это должно быть так же просто.

**Independent Test**: Запустить откат на предыдущую версию — health показывает её номер и sha, сайт отдаёт её
статику. Запустить откат «обратно» на новую — снова новая.

**Acceptance Scenarios**:

1. **Given** на коробке стоит версия N, **When** запускается откат на версию N−1, **Then** в пределах 10 минут health
   показывает номер и sha N−1, статика сайта — от N−1, в GitHub деплой N−1 успешен и активен.
2. **Given** указан номер, которого нет среди опубликованных версий, **When** запускается откат, **Then** он
   отказывает до создания деплоя, с понятной причиной.
3. **Given** откат на N−1 выполнен, **When** запускается деплой N, **Then** коробка возвращается на N.
4. **Given** посторонний без права записи в репозиторий, **When** пытается запустить откат, **Then** GitHub не даёт
   его выполнить.

### User Story 5 - Процесс записан так, что новая сессия работает по нему без подсказок (Priority: P5)

В `docs/DELIVERY.md` описан процесс: окружения, ветки и PR, коммиты, релизы, деплой, ресурсы (включая список
ресурсов AWS старого стека), откат, кто что жмёт; плюс ссылка на архитектуру проекта и порядок SDD. CLAUDE.md
проекта, конституция ALUMA и `deploy/README.md` ссылаются на него и больше не утверждают, что деплой — ручной.

**Why this priority**: Будущие сессии и владелец должны делать поставку и откат, не восстанавливая процесс по коду;
документ — образец для остальных проектов флота.

**Independent Test**: Сессия без контекста по одной только документации выполняет изменение через PR и откат —
без вопросов дирижёру.

**Acceptance Scenarios**:

1. **Given** `docs/DELIVERY.md`, **When** его читают, **Then** в нём есть все темы из FR-027, и каждая команда или
   действие в нём проверены на живом пайплайне.
2. **Given** факт процесса изменился, **When** его меняют, **Then** правится одно место, остальные на него ссылаются.

### Edge Cases

- **Находка при проверке истории** — стоп до решения дирижёра (ротация и/или чистка истории); видимость не меняется;
  значения находок нигде не печатаются.
- **Журналы прошлых прогонов Actions и их артефакты** станут публичными вместе с репозиторием — входят в проверку
  перед сменой видимости.
- **PR из чужих форков** после публикации — их проверки идут без секретов и без права создавать деплои; первый PR
  от нового участника требует одобрения запуска.
- **Два слияния подряд.** Версии получают разные номера по порядку; ставится последняя; ни одна установка не идёт
  параллельно с другой.
- **Запрос деплоя старше уже стоящей версии** (задержался в очереди) — агент берёт только самый новый запрос;
  наблюдатель старого, увидев более новый запрос, помечает старый неактуальным, а не проваленным.
- **GitHub недоступен или отвечает ошибкой** — агент ничего не меняет на коробке, повторяет попытку на следующем
  опросе; сайт продолжает работать на текущей версии.
- **GitHub отказал или замедлил анонимные git-запросы с IP машины** — агент пропускает чтение, увеличивает интервал и
  коробку не трогает; лимит REST API агент не расходует вовсе (разбор — research.md).
- **Ссылку окружения подвинули не конвейером** (руками, в обход правила) — агент поставит только коммит опубликованной
  версии с полным набором файлов релиза и совпавшими суммами; иначе не ставит ничего и пишет причину в журнал.
- **Публичный health отвечает не тот стек** (старые записи DNS в кешах ещё ведут в AWS; кеш; подмена) —
  наблюдатель требует совпадения и номера, и полного sha; иначе — «провал» по таймауту, коробку это не трогает.
- **Контрольная сумма не совпала / артефакт недокачан** — не ставится ничего.
- **Локальная проверка здоровья провалена** — автоматический возврат на предыдущую рабочую версию; этот запрос
  деплоя агент больше не повторяет (повтор — новым запуском деплоя/отката).
- **Провалился и возврат** (например, диск заполнен) — агент прекращает попытки и пишет причину в свой журнал; сайт
  не остаётся с частично обновлённой статикой.
- **Перезагрузка коробки или остановка агента посреди установки** — после старта агент доводит состояние до
  согласованного: либо новая версия с успешной проверкой, либо прежняя.
- **Новая версия требует другого набора Python-зависимостей** — они ставятся в рамках деплоя; при откате —
  зависимости той версии, на которую откатываемся. Недоступен индекс пакетов — установка не удалась, стоит прежняя
  версия.
- **Новая версия требует новой переменной окружения или секрета** — агент секреты не создаёт и не меняет; такая
  версия провалит проверку здоровья и откатится; нужный шаг описывается в релизе и выполняется до деплоя.
- **Изменились файлы пользовательских юнитов** (`deploy/systemd/user/`) — поведение описано в Assumptions.
- **Откат на версию, чьего артефакта уже нет** (удалён или истёк) — откат отказывает с понятной причиной; изменения
  на коробке не делаются.
- **Ручные изменения на коробке в каталоге кода** — агент их не затирает молча: установка не выполняется, причина —
  в журнале агента, деплой в GitHub провалится по таймауту.
- **Сборка в режиме `--production` отказывает** (не все факты владельца заполнены) — релиз собирается в том же режиме,
  в котором сейчас собрана статика на коробке (просмотр), пока владелец не заполнит факты; переключение режима —
  одна явная правка.
- **Версия, поставленная до этой фичи** (сейчас на коробке `0.4.0-box`, sha не отдаётся) — первая версия пайплайна
  ставится поверх неё; автоматический возврат «на прежнюю» для неё невозможен как для опубликованной версии, это
  разовый переход, описанный в плане.
- **Схема базы** — версии в рамках этой фичи обязаны быть совместимы с живой базой в обе стороны; миграции схемы не
  входят (см. Assumptions).

## Requirements *(mandatory)*

### Functional Requirements

**Проверки и master**

- **FR-001** [флот]: На каждый push в любую ветку и на каждое открытие/обновление pull request GitHub MUST запускать
  проверки: линтер, сборку и полный набор тестов проекта (тот же, что локально). Зависимости проверок MUST браться
  из файлов зависимостей проекта (requirements / package-lock), а не списком в описании проверки. Права конвейера
  по умолчанию — только чтение кода; шире — только в заданиях релиза и деплоя, которым это нужно. Новый прогон той
  же ветки отменяет незаконченный старый. (Образец — CI УЗД, ветка `ci-checks`.)
  - [ALUMA]: тесты — `python -m unittest discover -s tests -t .` и мокнутые браузерные тесты `tests/redesign.spec.js`;
    сборка — `build.py` в режиме выпуска с кодом выхода 0.
- **FR-002** [флот]: Ветка master MUST быть защищена для всех, включая владельца, без обхода: слияние только через PR
  с зелёными обязательными проверками, 0 обязательных одобрений, запрет прямого push, запрет перезаписи истории и
  удаления ветки. В аварии защиту временно снимает владелец в настройках — это описано в `docs/DELIVERY.md`.
- **FR-003** [флот]: Для PR MUST быть включено автоматическое слияние после зелёных проверок; стандартный путь всех
  сессий — ветка → PR → авто-merge.
- **FR-004** [флот]: Проверки, которые пишут в живые базы или бьют по живому сайту, MUST NOT входить в автоматические
  проверки. [ALUMA]: `tests/smoke.spec.js` — только вручную и только против локального стека.
- **FR-004a** [флот]: Линтер MUST быть лёгким, не добавлять тяжёлых зависимостей и на момент включения давать ноль
  замечаний на master (замечания исправлены или правило осознанно отключено с причиной). Выбор инструмента и набора
  правил — в research.md.

**Версия и релиз**

- **FR-005** [флот]: После каждого слияния в целевую ветку, и ТОЛЬКО если все обязательные проверки на этом коммите
  зелёные, система MUST автоматически опубликовать новую версию SemVer `vX.Y.Z`: по умолчанию повышается patch;
  метка слитого PR `release:minor` / `release:major` повышает minor / major с обнулением младших частей; первая
  версия — `v0.5.0`. Тег ставится на этот коммит, GitHub Release содержит список изменений со времени прошлой версии.
- **FR-006** [флот]: Релиз MUST содержать артефакт — всё, что ставится на коробку, — и файл контрольных сумм SHA-256
  для каждого файла релиза. Артефакт MUST NOT содержать секретов и живых данных. [ALUMA]: артефакт — код API и
  собранная статика сайта этой версии.
- **FR-007** [флот]: Артефакт MUST собираться из коммита тега воспроизводимо. [ALUMA]: повторная сборка того же коммита
  даёт те же контрольные суммы статики.
- **FR-008** [флот]: Опубликованная версия MUST быть неизменной: номер не переиспользуется, артефакт и суммы не
  заменяются.
- **FR-009** [флот]: Эндпоинт здоровья проекта MUST после установки версии отдавать её номер (ровно имя тега `vX.Y.Z`)
  и полный git sha её коммита — без ручной правки окружения. [ALUMA]: `GET /api/fx/health` отдаёт `version` и
  `git_sha`; остальное в ответе и в поведении API не меняется, в Lambda и под gunicorn одинаково.

**Деплой**

- **FR-010** [флот]: Публикация версии MUST создавать в GitHub запрос деплоя этой версии в окружение `production`;
  при красных проверках запроса нет.
- **FR-010a** [флот]: Вместе с запросом деплоя конвейер MUST передвигать ссылку окружения `production` на коммит
  тега версии (вперёд при деплое, назад при откате); право записи — только у задания, которое её двигает. Двигать
  ссылку MUST только конвейер (правило репозитория); теги `v*` MUST создаваться только конвейером, а удалять и
  перезаписывать их MUST NOT никто (правило репозитория). Тогда даже при незащищённой ссылке окружения на коробку
  встанет только неизменный, выпущенный конвейером релиз. Оба правила MUST быть подтверждены реальным прогоном; если
  исключение для конвейера на ссылке окружения невозможно, действует запасной вариант из plan.md.
- **FR-011** [флот]: Агент на машине MUST сам регулярно забирать запросы деплоя (модель pull, без входящего SSH);
  сигнал для агента — ссылка окружения `production` (FR-010a); время от её сдвига до начала установки — не больше
  2 минут (чтение раз в минуту).
- **FR-011a** [флот]: Агент MUST отказываться от установки, если в каталоге кода на машине есть незакоммиченные
  изменения отслеживаемых файлов (установка стёрла бы их), и сообщать об этом в журнале; MUST иметь режим проверки
  без изменений («что будет поставлено, откуда, что изменится»); MUST вести журнал каждой установки и возврата:
  когда, что инициировало (релиз / откат / автоматический возврат), sha было → стало, итог — и печатать короткий
  итог. (Образец — `deploy-uzd`; отличие: без sudo и чужого пользователя, всё под `ihor` пользовательскими юнитами.)
- **FR-012** [флот]: Перед установкой агент MUST скачать артефакт версии и сверить контрольные суммы; при расхождении —
  ничего не ставить.
- **FR-013** [ALUMA]: Установка MUST: поставить код версии в каталог кода коробки, привести Python-зависимости к набору
  версии, опубликовать статику в `/srv/aluma` без промежуточного состояния, видимого гостю (новые файлы появляются
  вместе, старые удаляются после; права — читаемые для веб-сервера), перезапустить `ihor-aluma-api`.
- **FR-014** [флот]: После установки агент MUST проверить здоровье локально: сервис отвечает, номер и sha в ответе
  равны устанавливаемой версии, сайт отдаётся — в пределах заданного срока. [ALUMA]: API на 127.0.0.1:8005, главная
  страница из `/srv/aluma` — новой версии.
- **FR-015** [флот]: При провале локальной проверки здоровья агент MUST вернуть предыдущую рабочую версию тем же путём,
  проверить её здоровье и запомнить этот запрос деплоя как проваленный, чтобы не повторять его.
- **FR-016** [флот]: Статус каждого деплоя в GitHub (в процессе, успешно, провал, неактуален) MUST ставить конвейер
  встроенными правами (без личных токенов): он ждёт, пока публичный адрес health покажет номер И полный sha этой
  версии, и ставит «успешно»; по таймауту — «провал»; если появился более новый запрос деплоя — «неактуален».
  Окружение `production` в GitHub MUST показывать, какая версия сейчас активна. [ALUMA]: адрес публичной проверки —
  переменная окружения `production` `ALUMA_HEALTH_URL`; исходное значение — `https://table.central-aparts.store/api/fx/health`
  (DNS `table` переключён на коробку 2026-09-11, `a7e9c64`); `table-new` — только если дирижёр не принял переключение.
- **FR-017** [флот]: Одновременно MUST идти не больше одной установки; агент ставит то, на что указывает ссылка
  окружения в момент чтения; промежуточные сдвиги ссылки не ставятся.
- **FR-018** [флот]: Агент MUST NOT: слушать сетевые порты, использовать sudo, обращаться к Caddy (запуск, остановка,
  перезагрузка, порт 2019, admin-сокет), трогать что-либо вне территории проекта; процессы — только через свой юнит
  или по PID. [ALUMA]: территория — `/opt/ihor/aluma-table`, `/srv/aluma`, `~/.config/aluma/` и собственные
  пользовательские юниты ALUMA.
- **FR-019** [флот]: Агент MUST NOT менять и печатать живые данные проекта, файл окружения с секретами и сами
  секреты; в его журнал MUST NOT попадать секреты и персональные данные. [ALUMA]: живые данные — `data/` (SQLite с
  заявками), окружение — `~/.config/aluma/aluma.env`.
- **FR-020** [флот]: Агент MUST переживать перезагрузку машины (запускается сам) и после прерывания доводить состояние
  до согласованного (новая версия с успешной проверкой или прежняя).
- **FR-021** [флот]: У агента MUST NOT быть учётных данных GitHub и MUST NOT быть обращений к REST API GitHub:
  ссылку окружения и теги он читает анонимно по протоколу git (smart HTTP), артефакты и суммы — по прямым ссылкам
  скачивания релиза. Поэтому число агентов флота на одном IP не ограничено лимитом REST API. Агенту MUST NOT использовать токены, найденные на
  машине (в том числе уже залогиненный `gh`). Помощники учётных данных git из
  конфигурации пользователя при вызовах агента MUST быть отключены. Агент MUST ставить только коммит, на который
  указывает тег опубликованной версии `vX.Y.Z` этого репозитория с полным набором файлов релиза.

**Откат**

- **FR-022** [флот]: В GitHub MUST быть одно действие «откат/деплой версии», принимающее номер ранее опубликованной
  версии, передвигающее на неё ссылку окружения и создающее запрос деплоя этой версии в `production`; дальше — тот
  же путь и те же проверки, что в FR-011…FR-017. Запускать его может любой с правом записи в репозиторий.
- **FR-023** [флот]: Действие отката MUST отказывать до создания деплоя, если такой версии нет или её артефакт
  недоступен.
- **FR-024** [флот]: Откат MUST NOT менять живые данные; откатываются код, зависимости и статика. Откат MUST быть
  проверен на деле (FR-029).

**Секреты и доступ к prod**

- **FR-025** [флот]: В репозитории MUST NOT быть ключей, токенов и паролей — только `.env.example`
  ([ALUMA]: `deploy/aluma.env.example`). Если пайплайну в GitHub нужен секрет, он хранится только в GitHub Secrets
  окружения `production`, а в репозитории — лишь имя и назначение. Секреты на машине — файлы 600 вне git.
- **FR-025a** [флот]: Окружение `production` в GitHub MUST быть защищено: запросы деплоя в него создаются только из
  master (релиз) и из действия отката; секреты окружения (если появятся) недоступны проверкам PR.
- **FR-026** [флот]: Журналы проверок, релизов и деплоев MUST NOT содержать секретов и персональных данных.

**Публикация репозитория**

- **FR-030** [флот]: До смены видимости на публичную MUST быть проверена вся история git (все коммиты всех веток и
  тегов, включая удалённые с GitHub ветки, если они есть локально) сканером секретов и поиском по шаблонам: токены,
  ключи AWS, пароли, файлы `.env`, `infra/samconfig.toml`, `dump/*.jsonl`, `data/*.db`, телефоны и имена из заявок.
  Выбор сканера — в research.md.
- **FR-031** [флот]: Проверка MUST NOT печатать найденные значения — только тип, коммит, путь и строку. Отчёт
  проверки MUST быть сохранён. Инфраструктурные идентификаторы (AWS account id, ARN сертификата в
  `infra/samconfig.toml.example`) MUST перечисляться в находках для решения дирижёра.
- **FR-032** [флот]: Любая находка MUST останавливать публикацию до решения дирижёра (ротация, чистка истории);
  видимость в этом случае не меняется.
- **FR-033** [флот]: Журналы и артефакты прошлых прогонов Actions, релизы, issues и PR репозитория MUST быть
  просмотрены на секреты и персональные данные до смены видимости.
- **FR-034** [флот]: Смена видимости, защита master (FR-002, FR-003), правила окружения `production` (FR-025a) и
  включение сканирования секретов и защиты от их push в GitHub MUST выполняться отдельным шагом после чистой
  проверки, с объявлением дирижёру до и отчётом после.

**Конвейер**

- **FR-035** [флот]: Версии actions в конвейере MUST быть закреплены; за основу — `actions/checkout@v6` и
  `actions/setup-node@v6`; `actions/setup-python` той же линейки MUST быть подтверждён реальным прогоном в пилоте;
  итоговые версии записываются в `docs/DELIVERY.md` для шаблона флота.

**Документация**

- **FR-027** [флот]: `docs/DELIVERY.md` MUST описывать то, что есть, а не план, по структуре образца УЗД:
  окружения; ветки, PR, коммиты; проверки (что запускается, что НЕ запускается и почему); релизы и нумерацию
  версий; выкат; секреты (честно: что где лежит, и что GitHub Secrets пусты, если пусты); ресурсы (в том числе
  список ресурсов AWS — ссылкой на `docs/AWS-TEARDOWN.md`); откат (автоматический и ручной); «Разрыв со стандартом
  флота» — честный список недоделанного; «Кто что нажимает» (конвейер, агент, владелец, сессии); что делать, если
  агент сломался, лимит API исчерпан или защиту пришлось снять. Плюс ссылки на архитектуру проекта и порядок SDD.
- **FR-028** [ALUMA]: `.specify/memory/constitution.md` (п.VI — по формулировке constitution-base 2.1.0), CLAUDE.md
  проекта (§9 и связанные места), `deploy/README.md` и `docs/CUTOVER-CHECKLIST.md` MUST быть приведены в
  соответствие: деплой на коробку — автоматический через конвейер, выкат вне конвейера — только с «да» владельца,
  ручные шаги обновления клона и публикации статики заменены ссылкой на `docs/DELIVERY.md`; в чек-лист переключения
  добавлена смена адреса публичной проверки health.

**Проверка вживую**

- **FR-029** [флот]: Фича MUST быть проверена реальным изменением: безобидная правка → PR → проверки → авто-merge →
  релиз → автодеплой → health показывает номер новой версии и именно sha её коммита → откат на прежнюю (health
  показывает прежние номер и sha) → деплой обратно на новую; каждый шаг подтверждён ответом GitHub или машины.

### Key Entities

- **Версия**: номер `vX.Y.Z`, тег, git sha коммита, дата, список изменений, метка повышения; неизменна после публикации.
- **Артефакт версии**: архив со всем, что ставится на машину; файл контрольных сумм SHA-256 к нему.
- **Запрос деплоя**: версия (тег), окружение `production`, что инициировало (релиз или откат), время создания.
- **Статус деплоя**: в ожидании / в процессе / успешно / провал / неактуален; причина; момент; ставит конвейер.
- **Окружение `production`**: машина ace-main; правила (откуда можно создавать деплои); адрес публичной проверки health.
- **Ссылка окружения**: ветка `production`; указывает на коммит опубликованной версии; двигает только конвейер;
  читает агент.
- **Агент деплоя**: программа и таймер на машине; без учётных данных; локальный журнал; блокировка «одна установка
  за раз»; память о проваленных запросах деплоя.
- **Установленная версия на машине**: номер, sha, что было до неё (для автоматического возврата).
- **Отчёт проверки истории**: дата, охват (коммиты, ветки, теги, прогоны Actions), находки без значений, решение.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: От слияния PR в master до того, как health коробки показывает номер и sha новой версии, проходит не
  больше 20 минут и ноль ручных действий.
- **SC-002**: Откат на любую из опубликованных версий — одно действие в GitHub; health показывает выбранную версию
  не позже чем через 10 минут.
- **SC-003**: 100% коммитов в master после включения защиты пришли через PR с зелёными обязательными проверками;
  ни один релиз и ни один деплой не созданы с красными проверками.
- **SC-004**: При провале локальной проверки здоровья коробка возвращается на прежнюю рабочую версию не позже чем
  через 10 минут после начала установки, а в GitHub деплой помечен проваленным.
- **SC-005**: Во время деплоя гость ни разу не получает страницу со ссылками на ещё не опубликованные файлы; перерыв
  ответа API на перезапуск — не больше 30 секунд.
- **SC-006**: В репозитории (во всей истории), журналах GitHub и журнале агента — ноль секретов и персональных данных
  на момент смены видимости и после (отчёт проверки истории + сканирование секретов GitHub).
- **SC-007**: Агент за всё время работы не открыл ни одного слушающего сокета, не выполнил ни одной команды через sudo,
  ни одного обращения к Caddy и ни одного запроса к GitHub с учётными данными (проверяется тестами агента).
- **SC-008**: Полная проверка реальным изменением (FR-029) пройдена от начала до конца, включая откат и возврат, с
  совпадением sha в health на каждом шаге.
- **SC-009**: Новая сессия по одной `docs/DELIVERY.md` проводит изменение через PR и выполняет откат без вопросов
  дирижёру.
- **SC-010**: Агент не делает ни одного запроса к REST API GitHub (ноль расхода лимита 60/ч на IP машины) —
  проверяется тестами агента и замером остатка лимита до и после суток работы.

## Assumptions

- Коробка ace-main — единственное окружение (`production`); отдельного staging нет. С 2026-09-11 основное имя
  `table` ведёт на коробку (переключение DNS — вне фичи); конвейер DNS не трогает.
- Модель pull одобрена дирижёром ALUMA и главным дирижёром: входящий SSH на машину и изменение firewall/SSH требуют
  «да» Дениса, а на машине четыре чужих бизнеса; разбор альтернатив (self-hosted runner, SSH из Actions) — в
  research.md. ALUMA — пилот; общая часть станет шаблоном для сайта и бек-офиса (`~/maestro/cicd/PLAN.md`).
- Репозиторий становится публичным (решение владельца 2026-09-11); на публичном репозитории защита ветки, окружения
  и сканирование секретов доступны на тарифе free, раннеры GitHub бесплатны.
- Секретов для проверок и конвейера не требуется: релиз и статусы — встроенными правами конвейера.
- Релиз собирается в том же режиме сборки, в каком сейчас собрана статика на коробке (просмотр, без Pillow), пока
  владелец не заполнил факты для `--production`; переключение — одна явная правка.
- Схема базы в рамках фичи не меняется; все версии совместимы с живой базой; миграции — отдельная фича.
- Секреты окружения (`~/.config/aluma/aluma.env`) остаются на коробке и не переносятся в GitHub; агент их не читает
  и не меняет. Номер и sha версии для health задаются механизмом деплоя, а не ручной правкой этого файла.
- Изменения в пользовательских юнитах ALUMA (`deploy/systemd/user/`) агент применяет к своим юнитам ALUMA в
  менеджере пользователя; изменения юнита самого агента вступают в силу со следующего запуска.
- Хранится как минимум последние 10 опубликованных версий, доступных для отката; более старые — по возможности.
- AWS, Lambda, DNS, блоки Caddy, другие проекты флота, smoke против живых баз — вне фичи. Старый AWS-стек удаляется
  отдельно (`docs/AWS-TEARDOWN.md`).
- Выкат: constitution-base 2.1.0, п.VI — автодеплой после попадания в целевую ветку разрешён (OWNER-RULES п.22), если
  CI зелёный и откат проверен; выкат вне конвейера — только с «да» владельца.
