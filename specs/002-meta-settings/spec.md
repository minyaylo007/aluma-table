# Feature Specification: Настройки, пиксель и Meta — одна страница для теста рекламы

**Feature Branch**: `noch/3-nastroyki` (папка фичи `specs/002-meta-settings`; отдельной git-ветки Spec Kit не создаёт)

**Created**: 2026-10-20

**Status**: Accepted for implementation (ускоренно, ночь 20→21.10; решения записаны ниже, владельца не ждём)

**Input**: Задание сессии (3) ночи 20→21.10 и общий контракт `~/maestro/tasks/aluma-noch-2026-10-20-obshchee.md`:
владелец утром открывает ОДНУ страницу настроек, вставляет то, что нужно для теста, — и всё работает без пересборки
сайта и без сессии; плюс полный комплект для запуска теста в Meta.

## Контекст

Сайт ALUMA переходит на витрину из 4–5 товаров в формате предзапуска (лист ожидания, денег не берём). Тест спроса —
реклама в Meta (Facebook/Instagram) на Израиль. Для теста нужны: пиксель на сайте, серверная отправка заявок в Meta
(чтобы заявки считались даже при блокировщиках), номер WhatsApp и контакты в футере. Сейчас всё это зашито в сборку
(`content.json`) — поменять можно только сессией и пересборкой. Эта фича выносит эти значения в настройки,
которые владелец меняет сам в `/admin`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Владелец заполняет настройки утром (Priority: P1)

Владелец входит в `/admin` (существующий вход), открывает «Настройки», вставляет Pixel ID, токен Conversions API,
номер WhatsApp, имя/телефон/e-mail/город, при желании Clarity ID и test event code, сохраняет. Через минуту сайт
сам показывает контакты и кнопку WhatsApp, на страницах работает пиксель.

**Why this priority**: без этого тест рекламы утром не стартует.

**Independent Test**: войти, сохранить поля, открыть `GET /api/fx/config` — там новые значения, без токена.

**Acceptance Scenarios**:

1. **Given** вход выполнен, **When** владелец сохраняет корректный Pixel ID и WhatsApp, **Then** страница показывает
   «сохранено», чек-лист отмечает ✓ у пикселя и WhatsApp, публичный конфиг отдаёт их.
2. **Given** токен CAPI сохранён, **When** страница открывается снова, **Then** токен не показывается — только
   «задан», и есть действия «заменить» и «стереть».
3. **Given** введён номер WhatsApp не в международном формате (например, буквы или 5 цифр), **When** «Сохранить»,
   **Then** ничего не сохраняется, у поля — понятная ошибка по-русски, введённые значения (кроме токена) остаются.
4. **Given** не выполнен вход, **When** открыть `/admin/settings`, **Then** переход на страницу входа.
5. **Given** любое сохранение, **When** смотрим журнал изменений, **Then** видно кто/когда/какое поле, без значений.

### User Story 2 — Проверка связи с Meta одной кнопкой (Priority: P1)

На странице настроек кнопка «Проверить» отправляет в Meta тестовое серверное событие (с test event code, если он
задан) и показывает «ок» или «ошибка» с кодом — без тела ответа Meta.

**Independent Test**: с моком сети — «ок» на 200, «ошибка (код)» на 4xx/исключение; токен не попадает в вывод и лог.

### User Story 3 — Заявка уходит в Meta сервером (Priority: P1)

Посетитель оставляет заявку. Она сохраняется первой; затем владельцу уходит Telegram (с товаром, размером, тонировкой,
сроком), затем — событие Lead в Meta Conversions API с тем же `event_id`, что и у браузерного пикселя (Meta считает
одну заявку, а не две). Телефон и e-mail уходят только хешами SHA-256 по правилам нормализации Meta.

**Acceptance Scenarios**:

1. **Given** пиксель и токен заданы, **When** реальная заявка, **Then** ровно один запрос в Meta с `event_name=Lead`,
   `event_id` из заявки, хешированным телефоном, `fbp/fbc` из cookie, IP и user-agent.
2. **Given** заявка с `x-test: 1`, **Then** в Meta ничего не уходит (как и в Telegram).
3. **Given** Meta отвечает ошибкой или недоступна, **Then** заявка сохранена, гость видит успех, в логе одна строка
   `capi_failed` без токена и без тела ответа.
4. **Given** токен или пиксель не заданы, **Then** запросов в Meta нет вообще.

### User Story 4 — Сайт сам подхватывает трекинг (Priority: P1)

`site/assets/tracking.js` при загрузке страницы берёт публичный конфиг, ставит Meta Pixel только если задан Pixel ID,
Clarity — если задан Clarity ID, и даёт сайту `window.alumaTrack(event, params)`. Каждое событие получает `event_id`
и дублируется в свою аналитику `/api/fx/event`. Без пикселя всё работает тихо, без ошибок в консоли. Работает на
иврите (RTL, `/`) и на английском (`/en/`).

### User Story 5 — Разбор заявок теста (Priority: P2)

В `/admin` у заявки видны товар, размер, тонировка, опоры, город, срок покупки, предпочтительный канал; есть фильтр
по товару и выгрузка CSV для разбора теста.

### User Story 6 — Комплект запуска теста в Meta (Priority: P2)

`docs/META-TEST.md` по-русски: структура кампании, 3 креатива на иврите, UTM-шаблон, KPI и критерии стоп/успех,
чек-лист на утро, скрипты ответов в WhatsApp на иврите. В Meta ничего не создаётся.

### Edge Cases

- Конфиг недоступен (сеть, 500) — сайт работает, трекинг тихо выключен, контакты скрыты.
- Владелец стирает Pixel ID — через ≤ 60 с (кеш) пиксель на новых загрузках не ставится.
- Владелец открыл сайт с `?me=1` (cookie `fx_me`) — пиксель и Clarity не грузятся, события не пишутся.
- Посетитель не согласился с уведомлением о cookie — сторонний код не грузится (принцип текущего сайта сохраняется).
- Повторная отправка заявки той же формой — Meta получает тот же `event_id` и склеивает.
- Поле настроек длиннее лимита / с HTML — обрезается/экранируется, XSS в админке невозможен.
- Запрос на сохранение настроек с чужого сайта (CSRF) — отклоняется.

## Requirements *(mandatory)*

### Functional Requirements

**Настройки**
- **FR-001**: Страница `/admin/settings` доступна только после существующего входа `/admin`.
- **FR-002**: Поля и проверки:
  | Поле | Ключ | Проверка | Публичное |
  |---|---|---|---|
  | Имя для сайта/футера | `contact_name` | ≤ 80 символов | да |
  | Телефон | `contact_phone` | пусто или `+` и 8–15 цифр (пробелы/дефисы допускаются при вводе, хранится `+цифры`) | да |
  | E-mail | `contact_email` | пусто или формат e-mail, ≤ 120 | да |
  | Город | `contact_city` | ≤ 60 | да |
  | WhatsApp | `wa_number` | пусто или международный: 8–15 цифр, первая не 0; хранится только цифры (как в wa.me) | да |
  | Meta Pixel ID | `pixel_id` | пусто или 10–20 цифр | да |
  | CAPI access token | `capi_token` | секрет; 20–400 символов без пробелов | **нет** |
  | Test event code | `test_event_code` | пусто или 3–40 латинских букв/цифр | **нет** |
  | Clarity ID | `clarity_id` | пусто или 6–20 латинских строчных букв/цифр | да |
  | Режим предзапуска | `launch_mode` | вкл/выкл, по умолчанию **вкл** | да |
- **FR-003**: Ошибка хотя бы в одном поле — не сохраняется ничего; ошибки показываются у полей по-русски.
- **FR-004**: Токен CAPI после сохранения никогда не выводится: ни в HTML, ни в JSON, ни в логе. Страница показывает
  «задан / не задан». Пустое поле токена при сохранении = «не менять»; отдельный флажок «стереть токен».
- **FR-005**: Каждое изменение пишет в журнал запись: время, кто (логин админки), поле, действие
  (`set`/`cleared`) — без значения. Страница показывает последние 20 записей.
- **FR-006**: Рядом с каждым полем — короткая инструкция по-русски (где взять Pixel ID, как сделать токен CAPI:
  Events Manager → Settings → Conversions API → Generate access token; где номер WhatsApp Business и т. д.).
- **FR-007**: Кнопка «Проверить связь с Meta»: тестовое событие в CAPI (с test event code, если задан); итог
  «ок» или «ошибка» + HTTP-код; тело ответа Meta не показывается и не логируется.
- **FR-008**: Чек-лист готовности на странице: пиксель ✓/✗, токен ✓/✗, WhatsApp ✓/✗, контакты ✓/✗ (имя и телефон
  или e-mail), последнее событие PageView и Lead по своим событиям (время), последняя заявка (только время),
  последняя отправка в CAPI (время, ок/ошибка, код).
- **FR-009**: POST настроек принимается только с того же сайта: если заголовок `Origin` есть и его хост не совпадает
  с `Host` — 403. Cookie входа уже `SameSite=Lax` и `Path=/admin`.

**Публичный конфиг**
- **FR-010**: `GET /api/fx/config` → JSON строго по контракту `contracts/config.md`: `pixel_id`, `wa_number`,
  `clarity_id`, `contact{name,phone,email,city}`, `launch_mode`. Незаданное — `null`. Без токена и test event code.
  `Cache-Control: public, max-age=60`.

**Трекинг**
- **FR-011**: `site/assets/tracking.js` — контракт `contracts/tracking.md`: тянет конфиг, ставит Pixel/Clarity по
  наличию ID и согласию, `window.alumaTrack(event, params)` возвращает `event_id`, дублирует событие в `/api/fx/event`.
  События: PageView, ViewContent, Lead, Contact, CustomizeProduct.
- **FR-012**: Нет пикселя — нет запросов к Meta, нет ошибок; `alumaTrack` всё равно пишет в свою аналитику.

**Заявка и Conversions API**
- **FR-013**: `POST /api/fx/lead` принимает дополнительно: `product_id`, `size_label`, `finish_id`, `base_id`,
  `timeframe` (`now` | `1-3m` | `later`), `contact_pref` (`whatsapp` | `call`), `email` (необязательно), `event_id`,
  `fbp`, `fbc` (контракт `contracts/lead.md`). Неизвестное значение — записывается как пустое, заявку не отклоняет
  (как сейчас у `color`/`size`). Старые поля, проверки, honeypot и лимиты — без изменений.
- **FR-014**: После сохранения реальной заявки (не `x-test`) сервер отправляет в CAPI событие Lead: тот же `event_id`,
  `action_source=website`, `event_source_url`, `user_data` с SHA-256 от нормализованных телефона (цифры с кодом страны,
  без `+`) и e-mail (нижний регистр, без пробелов), страна `il` хешем, `fbp`/`fbc` (из тела или cookie `_fbp`/`_fbc`),
  `client_ip_address`, `client_user_agent`; `custom_data` — товар, без персональных данных.
- **FR-015**: Отправка в CAPI — best effort, как Telegram: таймаут ≤ 5 с; ошибка → одна строка лога
  `{"event":"capi_failed", "id", "status"|"error"}` без токена (вырезается) и без тела ответа.
- **FR-016**: Telegram-уведомление владельцу дополняется товаром, размером, тонировкой, опорами, сроком покупки,
  каналом связи.

**Админка заявок**
- **FR-017**: Таблица заявок показывает новые поля; фильтр `?product=<id>`; ссылка «CSV» → `/admin/leads.csv`
  (те же фильтры диапазона/теста/товара), только после входа, защита от формул в ячейках (`=+-@` → префикс `'`).

**Документ**
- **FR-018**: `docs/META-TEST.md` по-русски, содержание — User Story 6; цены и сроки помечены как предварительные
  («מחיר משוער, טרם אושר»), поправка главного 20.10 22:45.

### Key Entities

- **Настройки** — одна запись: поля FR-002 + `updated_at`, `updated_by`. Хранится в той же базе, что заявки.
- **Запись журнала настроек** — время, кто, поле, действие. Без значений.
- **Статус CAPI** — время последней отправки, ок/ошибка, HTTP-код, источник (`lead`/`test`).
- **Заявка** — существующая + поля FR-013.

## Success Criteria *(mandatory)*

- **SC-001**: Владелец заполняет настройки и видит чек-лист «всё ✓» меньше чем за 10 минут, без сессии и пересборки.
- **SC-002**: Изменение настройки видно на сайте не позже чем через 60 секунд.
- **SC-003**: 100 % реальных заявок сохраняются даже при недоступной Meta/Telegram (тест с отказом сети).
- **SC-004**: Токен CAPI не встречается ни в одном ответе сервера, ни в одной строке лога (тест-поиск по выводу).
- **SC-005**: Каждая заявка с пикселем даёт в Meta одно событие Lead (браузер + сервер с одним `event_id`).
- **SC-006**: Сайт без заданного пикселя не делает ни одного запроса к доменам Meta.

## Решения (вместо уточнений — ночь, владельца не ждём)

1. **Хранение** — новая таблица `fx_settings` в той же SQLite через существующий shim `api/store.py` (ключ `pk`+`sk`):
   `SETTINGS/current`, `CAPI/status`, `AUDIT/<ts>#<id>`. Только `put_item`/`get_item`/`query` — новых выражений
   в shim не нужно. В режиме DynamoDB таблица `SETTINGS_TABLE` (не выкачено, не создаём — AWS только чтение).
2. **Секрет в базе открытым текстом** — база уже содержит персональные данные заявок и лежит вне git, права 600 у
   юнита; шифрование ключом из env добавило бы второй секрет без выигрыша. Токен CAPI — узкий (только отправка
   событий в один пиксель). Записано как принятый риск.
3. **Согласие на cookie** — сохраняем принцип текущего сайта: сторонний код только после «ОК» в уведомлении
   (`localStorage fx_notice_v1 = "1"`). Если на странице нет своего блока `#notice`, `tracking.js` показывает
   свой минимальный (he/en по `<html lang>`). Без пикселя и Clarity уведомления нет.
4. **Режим предзапуска** — только флаг в конфиге; что показывать — решает витрина (сессия 1).
5. **CSRF** — проверка `Origin` на POST настроек + существующий `SameSite=Lax`; токенов форм не вводим.
6. **Версия Graph API** — `v23.0`, переопределяется `META_GRAPH_VERSION` в env.
7. **Кто в журнале** — логин админки (`ADMIN_USER`, он один) + хеш IP.
8. **Новых зависимостей нет**: `requests` уже есть.
9. **test_event_code — только для кнопки «Проверить»**: настоящие заявки уходят без него, иначе Meta не учтёт их
   в оптимизации кампании.

## Assumptions

- Вход в админку один (`ADMIN_USER`/`ADMIN_PASS`), ролей нет.
- Форма сайта (сессия 1) передаёт поля FR-013 и `event_id`, полученный от `alumaTrack`.
- Номер WhatsApp и контакты владелец введёт сам; пустые значения скрывают блоки на сайте.
- Нагрузка — единицы заявок в день; кеш конфига 60 с достаточен.
